# 安卓主题闪烁诊断

状态：2026-09-22 安卓真机复测仍闪，尚未修复。用户已确认：先访问四个 Tab，再手动切换主题，首次切到其它 Tab 会短暂出现旧主题的整页内容，第二次正常；深浅双向均有。

本轮只增加默认关闭的时序诊断。它不等待渲染、不改变切页流程、不添加遮罩、不写入或上传数据。前一轮底色、原生栏与 tabBar 试修没有消除真机闪烁。

## 收集一次复现

1. 重新编译当前代码，用微信开发者工具的「真机调试」连接安卓手机。下面的命令在连接手机的调试 Console 中执行，不是在模拟器 Console 中执行。
2. 手机上先访问看板、物品、今天、我的，停在“我的”。在 Console 执行：

   ```js
   getApp().startThemeTrace()
   ```

   返回 `enabled: true` 表示已开启；`trackedInstances` 是已注册页面与底栏实例的总数。若为 0，请确认连的是当前代码的真机调试会话。

3. 手机上手动切换深浅主题，按平常速度点到“物品”，再回“我的”，再点一次“物品”。记下第一次/第二次是否闪。随后执行：

   ```js
   console.log(JSON.stringify(getApp().stopThemeTrace()))
   ```

4. 将这段 JSON 与观察到的闪烁情况一起提供给开发者。反向切换可重复第 2–3 步，分别收集，避免一次日志太长。

诊断只保留最近 400 个事件；`dropped > 0` 说明早期事件被覆盖，应缩短复现重试。重复 `startThemeTrace()` 会开始新会话；`stopThemeTrace()` 还原原始 `setData`，重启后默认关闭。需要中途查看可用 `getApp().readThemeTrace()`，它不会停止收集。

如果开启真机调试后闪烁消失，也请记录这个差异，不能用调试会话中的结果替代普通预览验收。诊断增加完成回调，会影响少量调度时序；只在复现时短暂启用。

## 日志的含义

- `theme-change`：主题广播；`effectiveDark` 是应用当前主题，`themeRevision` 是本会话主题广播序号。
- `theme-send`：某个实例发出主题 `setData`；`request` 是本次请求编号，`requestedDark` 是本次要求的主题。
- `theme-ack`：同一请求收到界面更新完成回调。不要把回调时 `state.dark` 的当前值当成本次请求确认的主题，应按 `request` 配对；`requestRevision` 保留发送时的主题序号，避免快速双向切换时混淆。
- `attach / show / hide / detach`：实例创建、显示、隐藏、卸载；`instance` 可区分同一路由重建。
- `switch-call / switch-success / switch-fail`：原生切页调用及返回；成功回调不是屏幕已展示正确颜色的保证。
- `snapshot`：开启时已有实例的逻辑状态；它不是之前渲染完成的证明。

诊断只记录固定页面名、实例编号、布尔主题/内容门控、底栏选中序号、时序及四个固定 Tab 路径；不包含物品名称、备注、搜索内容、照片或缓存记录，不持续打印控制台。

判读时先按目标页面的 `instance` 找到最近一次 `theme-change` 对应的主题请求，再比较：

| 观察到的顺序 | 下一步 |
| --- | --- |
| 目标页当前请求已在 `switch-call` 前收到 `theme-ack`，仍闪 | 等待这个回调无益；继续定位视图展示/合成阶段，不能直接宣称是微信缓存 |
| 目标页回调晚于点击，但隐藏时也能完成 | 可试验只等待目标页实际待完成的更新，必须有取消及超时放行 |
| 目标页总在 `show` 之后才回调 | 不能严格等待回调再切页，否则可能相互等待；单次顺序不能证明因果 |
| 切页出现新的 `attach`/实例编号 | 检查实例重建和首次初始化路径，不能把“访问过”当作实例仍存活的证据 |

微信官方接口说明区分了同步更新的 `this.data`、异步传递到视图层的数据，以及界面更新完成回调：[官方 API 类型说明](https://github.com/wechat-miniprogram/api-typings/blob/master/types/wx/lib.wx.component.d.ts)。这些回调并不能直接观测手机屏幕的实际合成帧，因此最终仍以普通模式真机观感为准。
